# ADR 0003 — A bundled lexical evidence index, not a vector database

- **Status:** accepted
- **Date:** 2026-08-18

## Context

PS7 wants every recommendation backed by cited evidence from official sources. The
proposed stack named PostgreSQL + pgvector (or Supabase) with embedding-based
retrieval, plus Docling for document extraction.

Our corpus, once built: **1,545 chunks** — 1,141 MITRE ATT&CK techniques and group
profiles, 400 CISA KEV entries, 4 analyst-verified CERT-In advisories. 474 KB
gzipped. Queries against it are overwhelmingly identifier-shaped ("T1550.002",
"CVE-2026-34486") or short security phrases.

## Decision

**Build the index offline (`scripts/build_evidence_index.py`) into a committed,
read-only `index.json.gz`, and retrieve at request time with BM25 plus an exact
ATT&CK/CVE identifier boost and curated phrase→technique expansion
(`src/shared/evidence.py`). No embedding model, no vector database, no network at
query time.**

Interfaces exist (`EvidenceRepository`, `Chunk`) so a pgvector implementation could
be added later; it would have to pass the same tests.

## Why

**At this corpus size the retrieval bottleneck is not semantics, it is identifiers.**
An analyst investigating T1550.002 wants the T1550.002 page. Exact-ID matching gets
that right every time; cosine similarity gets it right most of the time. We weight
an exact identifier at 12.0 against BM25 scores that top out near 30, and
`tests/test_evidence.py` asserts the ID hit wins.

**We measured it instead of assuming.** `reports/retrieval_eval.md`, generated by
`scripts/eval_retrieval.py` over a 14-query hand-written gold set:
**recall@1 0.643, recall@5 0.857, MRR 0.717, 0 citation-integrity failures.** The
misses are published too, and they are the honest weakness of a lexical retriever: a
fully paraphrased query with no shared vocabulary ("logs in with a legitimate account
instead of malware" vs "Valid Accounts") still misses.

**A vector database on a free tier is a demo liability.** Supabase free projects pause
after a week of inactivity. The alternative — embedding at request time — needs
`sentence-transformers` and a model download in an image we keep deliberately slim.

**Provenance is the actual product, and it is orthogonal to the retriever.** Every
chunk carries URL, publisher, authority tier, section, the document's own date, our
retrieval time, extraction method and a SHA-256 of the text. That is what makes a
citation checkable. A vector store would not add one field to it.

**Extraction: no Docling, no PDF parsing.** The sources are already structured —
ATT&CK ships STIX JSON, KEV ships JSON, and CERT-In has no machine-readable feed at
all, so those four advisories are analyst-transcribed and marked `verified: true`.
Adding a layout-aware PDF extractor and its model weights to parse documents we do
not parse would be pure weight.

## Consequences

- The index is a **build artifact committed to the repo** (474 KB), so a fresh clone
  retrieves with no network. `scripts/build_evidence_index.py --no-network` rebuilds
  the ATT&CK and CERT-In halves offline; a failed KEV fetch carries the previous
  snapshot forward and labels it stale rather than silently dropping 400 chunks.
- KEV freshness is bounded by when the index was last built. The UI shows
  `index built <timestamp>` on every evidence panel; there is no way to read a stale
  citation without seeing its age.
- CVSS is `unknown` by default: KEV does not publish it and the NVD API is
  rate-limited. The prioritiser drops the factor and lowers confidence rather than
  scoring it zero.
- ATT&CK technique mappings for KEV entries are computed **at build time** and baked
  into the chunk identifiers. Doing it per request cost 5.9 s on the vulnerability
  screen; it is a pure function of the advisory text, so it belongs in the artifact.

## What would change our mind

- A corpus beyond roughly 50k chunks, or one where full advisory prose (not just
  titles and IDs) is the unit of retrieval.
- Measured recall@5 that a local embedding re-rank beats materially on the same gold
  set — the upgrade path is written down in `reports/retrieval_eval.md`, and this
  repo already ships MiniLM technique embeddings for it.
- Users needing to add their own documents at runtime, which is the point where a
  read-only build artifact stops working.
